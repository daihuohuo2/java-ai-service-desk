# 第三课：从错误输入读懂 HTTP

## 一次修改请求

Products.tsx 提交 PUT `/api/admin/products/P100`，请求包含 id=P100、name、category、priceCents、description、active。Security 先检查管理员角色和 CSRF，Controller 再通过 Update 分组校验，检查路径 ID 与正文 ID 一致，然后调用业务服务。新增 POST 的 Create 组禁止客户端指定 ID，由服务端生成。

ValidationGroups.Create/Update 继承 Default：指定组时仍执行通用的 NotBlank/Size/Min/Max。否则容易出现只验证 id，却漏掉金额和名称的错误。

EnumValue 是自定义约束；initialize 收集 TicketKind 的合法枚举名，isValid 检查输入。null 交给 NotBlank 处理，因此约束可以用于可选字段。业务服务也保留种类检查，因为服务可能从其他入口调用，HTTP 校验不是全部业务规则。

## 响应如何经过后端和前端

```json
{"code":0,"message":"成功","data":{"id":"P100","name":"阅读灯"}}
```

```json
{"code":400,"message":"输入格式不正确，请检查必填项和长度","data":{"id":"修改时必须携带商品编号"}}
```

```json
{"code":409,"message":"工单已被更新，请刷新后重试","data":null}
```

成功用 code=0，错误使用对应 HTTP 状态码。HTTP 本身仍分别是 200/400/409，不能全部强行返回 200。ApiResponseAdvice 只给控制器 JSON 包一层，遇到已经是 ApiResponse 的对象直接返回；ApiAdvice 捕获业务异常和校验异常，SecurityConfig 处理进入 Controller 之前的 401/403。

前端 api.ts 统一获取 Cookie/CSRF、发送请求、检查响应并返回 data。页面用 `api<PageResult<Order>>` 等泛型标注预期数据。TypeScript 类型帮助编译期检查，但不会自动证明网络 JSON 的所有嵌套字段都合法；当前封装检查响应协议，深层 schema 校验可作为后续练习。

## 不同传输协议的边界

| 场景 | 输出 |
|---|---|
| 普通 API JSON | ApiResponse |
| CSV 下载 | 原始 text/csv 文件内容，不把文件放进 JSON |
| SSE | phase/result/done/error 事件；result 是 ChatAnswer，error 有 error 文本 |
| 退出登录 | HTTP 204，没有 JSON 正文 |
| Actuator | 框架自己的健康检查响应，如 {status:UP} |
| CORS 在框架层拒绝 | 可能为纯文本 403；前端有非 JSON 错误兜底 |

SSE 的 phase 表示进度，result 才是经后端校验的业务结果；连接中途断开不能当成功。历史消息保存类型明确的 ChatAnswer 快照，重放不再使用随意拼装的 Map。

## 练习

在 Network 比较四次请求：未登录查订单（401）、客户访问管理员商品（403）、修改商品不带 id（400 字段错误）、两个客服用相同 version 修改（一个成功，一个 409）。说清楚失败发生在过滤器、参数校验还是业务层。

不要为了测试去破坏正常业务分支。使用隔离演示环境，以及 FullstackIntegrationTest 的 groupedValidationAndPathConsistencyProtectProductUpdates、customKindValidationReturnsFieldError 等现成测试。
