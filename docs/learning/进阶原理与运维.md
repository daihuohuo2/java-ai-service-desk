# 进阶原理：用当前项目理解面试知识

这里区分已实现机制和需要继续练习的主题。读懂一个机制后，用断点、日志或实验验证，避免只背框架名称。

## Java 与集合

- 从 FullstackBasics 看接口、多态、泛型、record 和 equals/hashCode。再比较 ArrayList 的随机访问、HashMap 的键查找、LinkedHashSet 的去重顺序。
- 泛型编译期检查与类型擦除是什么？为什么 Object 强转可能在运行时失败？
- 异常分类、try/finally/try-with-resources；数据库连接、文件流、线程池各由谁关闭？
- 集合、栈、队列、二分查找、排序和时间复杂度单独训练。用“查订单去重”和“分页排序”解释空间/时间代价，不宣称业务系统覆盖了所有算法。

## Spring 与事务

从构造注入追踪 OrderController/OrderService/OrderMapper 的创建。理解 Bean、组件扫描、配置绑定、自动配置和代理。Spring MVC 负责 HTTP 映射，Spring Security 在控制器前处理认证和授权。

ProductService.save 的商品修改、catalog_revision 递增和审计写入共同提交。事务传播、异常回滚条件、同类直接调用绕过代理，是独立于“加了注解”的知识。订单分页使用 REPEATABLE_READ 让 count 与列表共享快照；不要把它理解为所有请求互相阻塞。

参考：[Spring 事务文档](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)、[MyBatis Spring Boot 兼容表](https://mybatis.org/spring-boot-starter/mybatis-spring-boot-autoconfigure/)。

## 并发与 JVM

阅读 ConcurrencyLab，再找 AiGateway 中的 Semaphore、Future.get(timeout)、cancel(true)；ChatController 使用虚拟线程。要会解释：信号量限制资源使用数量，线程池安排工作，二者不是同一个概念。取消是协作请求，阻塞的第三方调用或远端服务不一定立即停止。

用 `jps -l` 确认项目 Java PID 后运行 `scripts/diagnose.ps1 -JavaProcessId <PID>`。它只查看端口、JVM 版本、堆信息和线程栈，不停止进程。诊断结果可能含本机信息，应保存在 .runtime。

继续学习堆/栈/元空间、对象生命周期、GC、类加载、线程阻塞和死锁。练习先在有限内存的实验程序中观察 GC 日志，不在正在使用的服务里故意制造 OOM。面对“慢请求”，先区分数据库、模型调用、锁等待和 CPU，再决定调优位置。

## HTTP、网络与操作系统

打开浏览器 Network，观察登录前获取 CSRF → 登录 → Cookie 变化 → 订单 GET → 工单 POST 的真实顺序。解释 HTTP 方法、JSON、状态码、Cookie、SameSite、CORS 和 CSRF；已有 Session 方案可以使用，JWT/OAuth2 是按身份系统需求补充的主题。

SSE 是服务器向浏览器发送事件流，不等于 WebSocket 双向通道。api.ts 处理 UTF-8 分片与 CRLF，服务端只发送校验后的结果。Nginx 禁用代理缓冲并设置读取超时。

练习区分 DNS 解析、TCP 连接、TLS、HTTP 响应；知道 localhost 在浏览器、宿主机和容器里分别指谁。Linux 至少熟悉 pwd/ls/cd、文件权限、进程、ss、curl、日志、磁盘空间和环境变量。不要把敏感配置直接打印到公共日志。

## 缓存与分布式边界

当前 Redis 仅缓存公开商品目录，不缓存客户订单，不持久化会话。数据库版本键避免旧缓存被新写入复用，异常回源提高缓存故障时的业务可用性；仍需数据库版本查询。

进一步练习缓存穿透、击穿、雪崩与容量限制时，先制造可测量的场景。共享会话、跨实例限流、分布式锁尚未实现。若将来部署多个 API 副本，需要解决这些问题，不能因为用了 Redis 就宣称系统已支持任意水平扩容。

任务采用至少一次投递，SQL 条件更新抢占，lease_token 隔离旧执行者。进程崩溃后依靠租约恢复；重复索引属于允许的幂等更新，不应将同样方式直接套到扣款、发货等不可重复外部副作用。

参考：[Spring AMQP 官方说明](https://docs.spring.io/spring-boot/reference/messaging/amqp.html)。

## Linux、HTTPS、监控和回滚

1. 在自己的 Linux 环境安装 JDK 21、Node 24、Docker Engine/Compose，克隆仓库，运行 sh scripts/build.sh。
2. 从 .env.example 生成自己的 .env，替换数据库密码；文件权限设为 600。默认端口仍只绑定回环地址。
3. 使用 compose.yaml；需要时叠加 compose.middleware.yaml。不要将 Redis/RabbitMQ/数据库直接发布到公网。
4. 有域名和证书后，参考 deploy/nginx.https.example.conf 配置宿主机反向代理，设置 APP_ORIGIN、COOKIE_SECURE=true。正式模式还要求 APP_DEMO=false 和独立管理员密码；现有数据库账户的密码不会因为修改环境变量自动更新。
5. 可叠加 compose.observability.yaml，指标只在容器网络的 9090 端口开放，Prometheus UI 只绑定本机 19090。规则提供服务不可用/索引失败告警条件，尚未接入短信、邮件或 Alertmanager 通知接收端。
6. 发版前备份数据库和当前源码/镜像；先验证新版本，再切换流量。V2 是新增表和索引，回退前仍须确认旧代码与当前数据兼容，不能自动回滚数据库覆盖新增业务数据。

现有 backup.ps1/verify-restore.ps1 针对 PostgreSQL，不应直接用于 MySQL。MySQL 应另用 mysqldump 与新建隔离库验证恢复，再用于正式数据；当前数据库迁移测试不等于灾备恢复演练。

仓库 CI 会测试和构建，没有目标服务器凭据，因此不自动执行生产部署。HTTPS 配置是待替换域名/证书的示例；没有实际域名或服务器时不能声称线上验收完成。

## 微服务、Vue 与 AI 深化

Spring Cloud、Nacos、网关、服务间认证、熔断、链路追踪、分布式事务、Kubernetes 都属于后续专项；当前没有引入这些框架。先画出“API 负责业务、索引 worker 负责模型任务”的边界，再讨论独立进程部署、共享会话、消息协议版本和失败恢复。不要把同一个库中的多个 Service 类称为多个微服务。

Vue 3 可以作为相同订单 API 的第二个客户端练习。先比较 props、事件、状态、路由和表单，再决定是否需要迁移主界面；当前正式前端使用 React。

AI 方面已有引用约束与固定场景验收。继续收集未见问题，标注期望资料和行为，分别统计引用命中、拒答、错误执行、响应时延与降级率。大规模检索可评估 pgvector/Elasticsearch，但当前知识库仍是最多 200 个有效片段的内存排序，没有宣称大规模向量数据库能力。
